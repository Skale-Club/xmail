<objective>
Eliminate cron overlap and multi-instance race conditions (audit H8). After this plan, every cron callback in `src/server/jobs/index.ts` is gated by a Postgres advisory lock — so a slow `processQueue` tick (>60s) cannot overlap the next tick, and a multi-replica deployment of the server runs each tick exactly once across the fleet.

Purpose: Currently only `processOutreachSequences` has an in-process mutex (`isSequenceProcessing` flag at line 9, 31-38). The other six cron jobs (`processQueue`, `processHeldMessages`, `cleanupOldMessages`, `resetDailyLimits`, `processReplies`, `processBounces`) have NO protection. In dev (one process) this risks data races when a job exceeds its tick interval. In any multi-instance deploy (which the platform doesn't currently use but is on the horizon per audit), every replica runs every cron tick — that's N× concurrent inserts, N× emails sent, N× bounce processing. Postgres advisory locks solve both at zero infra cost (no Redis, no Zookeeper) because the lock is session-scoped and visible across all clients of the same Postgres database.

Output:
1. `src/server/lib/cron-lock.ts` exporting `runWithLock(jobName: string, fn: () => Promise<void>)` and `computeLockKey(name: string)`.
2. `src/server/jobs/index.ts` wraps all seven cron callbacks (including the existing outreach one) with `runWithLock`. The `isSequenceProcessing` flag is REMOVED since advisory lock supersedes it (belt-and-suspenders not needed; advisory lock is strictly stronger).

Postgres advisory lock semantics:
- `pg_try_advisory_lock(bigint)` — returns boolean. True if acquired (non-blocking), false if already held by another session.
- `pg_advisory_unlock(bigint)` — returns boolean. True if released, false if not held by current session.
- **Session-scoped**: lock is automatically released when the session (Postgres connection) ends. With postgres-js connection pooling, the SAME connection must call lock and unlock — otherwise unlock fails silently.
- **Critical**: postgres-js pool returns connections to the pool after each query. To guarantee same-session lock+work+unlock, the work MUST run on a single reserved connection. Drizzle's `db.execute()` borrows from the pool per call. The clean approach: use the underlying `postgres-js` client's `.reserve()` (or `.begin()` transaction wrapper) to pin to one connection for the lock duration.

Per CONTEXT.md SEC-04 decision: "use stable BIGINT key: `BigInt(djb2(jobName)) % BigInt(2^63)` or similar deterministic hash."

    **Option A (preferred — if postgres-js client `client` is exported):** Use `client.reserve()` which returns a reserved connection that can be released back to the pool.

    ```ts
    import { createHash } from 'node:crypto'
    import { client } from '../../db'  // adjust import if export name differs

    // SEC-04 — see .planning/debug/system-wide-audit-2026-05-16.md H8

    /**
     * Maps an arbitrary job name to a stable signed BIGINT (Postgres bigint range)
     * via SHA-256 → first 8 bytes → BigInt → masked to int64 signed range.
     */
    export function computeLockKey(name: string): bigint {
        const hash = createHash('sha256').update(name).digest()
        // Take first 8 bytes as big-endian, mask to signed 63-bit range
        let key = 0n
        for (let i = 0; i < 8; i++) key = (key << 8n) | BigInt(hash[i])
        // Signed bigint: ensure within (-2^63, 2^63). Mask to positive 63-bit:
        const SIGNED_MAX = (1n << 63n) - 1n
        return key &amp; SIGNED_MAX
    }

    /**
     * Runs `fn` only if the named advisory lock can be acquired immediately.
     * If the lock is already held (by this process or another), logs a skip and returns.
     * Always releases on the same connection.
     */
    export async function runWithLock(jobName: string, fn: () => Promise<void>): Promise<void> {
        const key = computeLockKey(jobName)

        // Reserve a single connection for the lock+work+unlock sequence
        const sql = await (client as any).reserve()
        try {
            const acquired = await sql`SELECT pg_try_advisory_lock(${key}::bigint) AS got`
            const got = Boolean(acquired?.[0]?.got)
            if (!got) {
                console.log(`[cron-lock] ${jobName} already running on another process/tick, skipping`)
                return
            }
            try {
                await fn()
            } finally {
                try {
                    await sql`SELECT pg_advisory_unlock(${key}::bigint)`
                } catch (unlockErr) {
                    console.error(`[cron-lock] ${jobName} unlock failed:`, unlockErr)
                }
            }
        } finally {
            // Release the reserved connection back to the pool
            try { await (sql as any).release?.() } catch {}
        }
    }
    ```

    **Option B (fallback — if no reserve() available):** Use a `BEGIN; SELECT pg_try_advisory_xact_lock; ... COMMIT;` transactional variant via Drizzle's `db.transaction(...)`. The `pg_try_advisory_xact_lock` is automatically released at transaction end — no manual unlock needed, no session-pinning issue. However, this wraps the entire job in one Postgres transaction, which may not be desirable for long-running jobs (10s+ holding a transaction = vacuum/replication pressure).

    ```ts
    // Option B body of runWithLock:
    await db.transaction(async (tx) => {
        const r = await tx.execute(sql`SELECT pg_try_advisory_xact_lock(${key}::bigint) AS got`)
        const got = Boolean((r as any)?.[0]?.got)
        if (!got) {
            console.log(`[cron-lock] ${jobName} already running, skipping`)
            return
        }
        await fn()
    })
    ```

    **Decision rule:** if `src/db/index.ts` exports a postgres-js client with `.reserve()`, use Option A. Otherwise use Option B. Document the choice in SUMMARY.md.

    **Defensive notes:**
    - Don't throw on lock failure — that would crash the cron tick and spam logs. Just log and return.
    - Don't throw on unlock failure — already inside finally; log and swallow.
    - The lock key is deterministic per name — two processes computing `computeLockKey('processQueue')` get identical bigint.

<risks>
- **Reserved-connection availability.** If `src/db/index.ts` doesn't export the raw postgres-js client, Option A in Task 1 won't work — fall back to Option B (`pg_try_advisory_xact_lock` + `db.transaction`). The transactional variant holds an open transaction for the entire job duration. For jobs that run >10s, this can impact Postgres vacuum/replication. Acceptable for current scale; revisit if jobs grow.
- **Lock not released on process kill -9.** Postgres advisory locks are session-scoped — when the connection dies, the lock is auto-released. So a `kill -9` followed by restart cleanly re-acquires. NO orphan lock risk.
- **Connection pool starvation.** Option A reserves a connection for the entire job duration. If many jobs run concurrently and the pool is small (e.g. pool size 10), this could starve API requests. Mitigation: postgres-js pool default is 10; SkaleClub has at most 4 concurrent jobs (5-min jobs aligned, 1-min processQueue). 4 reserved + 6 for API = OK. Document expected behavior in SUMMARY.md.
- **Renaming jobs is breaking.** The advisory-lock key derives from the job NAME string. Renaming `processQueue` → `processQueueV2` would compute a different key — two old-name instances and one new-name instance could overlap during deploy. Mitigation: stable names. Document in code comment.
- **Concurrent ticks across daylight-saving time.** `node-cron` handles DST; advisory lock guards against accidental double-fire. No special handling needed.
- **Postgres connection used by lock must be the same as unlock.** Option A pins explicitly via `.reserve()`. Option B uses transaction (automatic release at COMMIT) — bullet-proof. Either is safe.
</risks>
