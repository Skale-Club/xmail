<objective>
Rewrite `src/server/lib/cascade.ts::deleteOrganizationCascade` so it deletes every row that references a deleted organization, runs in a single transaction, and preserves shared user state (mailbox + passwordHash) for users who remain members of other orgs.

Purpose: Audit finding C2 (CRITICAL). Current implementation (a) leaves orphans in `outlook_mailboxes`, `email_accounts`, all outreach tables, and `user_notifications`; (b) is NOT transactional; (c) nulls `passwordHash` for ALL members of the deleted org, locking users out of orgs they still belong to. This is a data-integrity + user-lockout bug.

Output: A new `cascade.ts` that satisfies CRIT-01 success criteria 1 and 2 in ROADMAP.md, plus a verification script that seeds a multi-org user and asserts post-delete invariants.
</objective>

## Goal

`deleteOrganizationCascade(organizationId)` deletes every dependent row in a single Postgres transaction and preserves cross-org user state.

## Scope

**In scope:**
- Full rewrite of `src/server/lib/cascade.ts::deleteOrganizationCascade` per audit Fase 1 Bloco 1.1.
- Wrapping in `db.transaction(async (tx) => { ... })` so a mid-flight failure rolls everything back.
- Counting each member's memberships in OTHER orgs to decide whether to delete their mailbox / null their `passwordHash`.
- Deleting from the complete table set per audit C2 (outreach module, outlook_mailboxes, mail tables, suppressions, statistics, webhook_requests via webhooks, etc.).
- Adding `scripts/test-cascade-delete.ts` that seeds fixtures, calls the function, and asserts zero orphans + preserved cross-org state.

**Out of scope:**
- Adding a real test framework (Vitest/Supertest) — none installed in this repo (CLAUDE.md). The verification script is a plain `tsx` runner.
- RLS consolidation migration (Phase 13 QUA-03).
- Refactoring callers (`src/server/routes/organizations.ts`) beyond verifying the signature still matches.
- Audit-log table for sensitive operations (deferred per 10-CONTEXT.md).

3. Replace the function body with a single `await db.transaction(async (tx) => { ... })` block. Inside the transaction, in this exact order (leaf-first; FK-safe):
   ```
   // 1. Collect members BEFORE we drop organization_users
   const members = await tx.select({ userId: organizationUsers.userId })
     .from(organizationUsers)
     .where(eq(organizationUsers.organizationId, organizationId));
   const memberIds = members.map(m => m.userId);

   // 2. Delete outreach module leaves first
   await tx.delete(outreachEmails).where(eq(outreachEmails.organizationId, organizationId));
   await tx.delete(outreachAnalytics).where(eq(outreachAnalytics.organizationId, organizationId));
   await tx.delete(campaignLeads).where(eq(campaignLeads.organizationId, organizationId));
   await tx.delete(sequenceSteps).where(eq(sequenceSteps.organizationId, organizationId));
   await tx.delete(sequences).where(eq(sequences.organizationId, organizationId));
   await tx.delete(campaigns).where(eq(campaigns.organizationId, organizationId));
   await tx.delete(leads).where(eq(leads.organizationId, organizationId));
   await tx.delete(leadLists).where(eq(leadLists.organizationId, organizationId));
   await tx.delete(emailAccounts).where(eq(emailAccounts.organizationId, organizationId));

   // 3. Mail/mailbox-scoped tables — collect mailbox IDs first, then delete leaves
   const mboxes = await tx.select({ id: mailboxes.id })
     .from(mailboxes).where(eq(mailboxes.organizationId, organizationId));
   const mboxIds = mboxes.map(m => m.id);
   if (mboxIds.length) {
     await tx.delete(mailMessages).where(inArray(mailMessages.mailboxId, mboxIds));
     await tx.delete(mailFolders).where(inArray(mailFolders.mailboxId, mboxIds));
     await tx.delete(mailFilters).where(inArray(mailFilters.mailboxId, mboxIds));
     await tx.delete(signatures).where(inArray(signatures.mailboxId, mboxIds));
     await tx.delete(contacts).where(inArray(contacts.mailboxId, mboxIds));
   }
   await tx.delete(outlookMailboxes).where(eq(outlookMailboxes.organizationId, organizationId));

   // 4. Webhook leaves (webhook_requests references webhooks.id, not org directly)
   const webhookRows = await tx.select({ id: webhooks.id })
     .from(webhooks).where(eq(webhooks.organizationId, organizationId));
   const webhookIds = webhookRows.map(w => w.id);
   if (webhookIds.length) {
     await tx.delete(webhookRequests).where(inArray(webhookRequests.webhookId, webhookIds));
   }
   await tx.delete(webhooks).where(eq(webhooks.organizationId, organizationId));

   // 5. Templates, tracking, statistics, suppressions
   await tx.delete(templates).where(eq(templates.organizationId, organizationId));
   await tx.delete(trackDomains).where(eq(trackDomains.organizationId, organizationId));
   await tx.delete(suppressions).where(eq(suppressions.organizationId, organizationId));
   await tx.delete(statistics).where(eq(statistics.organizationId, organizationId));

   // 6. Routing / messages
   await tx.delete(deliveries).where(eq(deliveries.organizationId, organizationId));
   await tx.delete(messages).where(eq(messages.organizationId, organizationId));
   await tx.delete(routes).where(eq(routes.organizationId, organizationId));
   await tx.delete(domains).where(eq(domains.organizationId, organizationId));
   await tx.delete(credentials).where(eq(credentials.organizationId, organizationId));
   await tx.delete(smtpEndpoints).where(eq(smtpEndpoints.organizationId, organizationId));
   await tx.delete(httpEndpoints).where(eq(httpEndpoints.organizationId, organizationId));
   await tx.delete(addressEndpoints).where(eq(addressEndpoints.organizationId, organizationId));

   // 7. Now delete remaining mailboxes (must be after mail-scoped leaves above)
   await tx.delete(mailboxes).where(eq(mailboxes.organizationId, organizationId));

   // 8. Drop memberships for THIS org
   await tx.delete(organizationUsers).where(eq(organizationUsers.organizationId, organizationId));

   // 9. For each former member, decide: are they still in another org?
   for (const userId of memberIds) {
     const stillMember = await tx.select({ id: organizationUsers.id })
       .from(organizationUsers)
       .where(eq(organizationUsers.userId, userId))
       .limit(1);
     if (stillMember.length === 0) {
       // Last org for this user → drop their personal stuff
       await tx.update(users)
         .set({ passwordHash: null })
         .where(eq(users.id, userId));
       // user_notifications has no direct FK to org — wipe per user since they have no org left
       await tx.delete(userNotifications).where(eq(userNotifications.userId, userId));
     }
     // else: user still belongs to another org → leave mailbox, passwordHash untouched
   }

   // 10. Finally, the org row itself
   await tx.delete(organizations).where(eq(organizations.id, organizationId));
   ```

## Risks / Notes

- **Risk: schema mismatch.** The audit-supplied table list may include tables that are exported under different identifiers in `src/db/schema.ts` (or don't have a direct `organizationId` column — some outreach tables may scope via parent). Mitigation: read `schema.ts` exhaustively before writing the deletes; if a table scopes through a parent (e.g. `outreach_emails.campaignId` rather than `organizationId`), delete via `inArray(parentIds)` instead of `eq(organizationId)`.
- **Risk: transaction-in-transaction in the verification script.** Drizzle supports nested transactions via savepoints but behavior varies by driver. If rollback-wrapping is unreliable, fall back to seeding with predictable UUIDs and cleaning up in `finally`.
- **Risk: `user_notifications` has no direct org FK.** Per audit C2, it should be deleted for the user only when they are no longer in any org. Verify in schema; if it scopes by something else (e.g. `metadata.organizationId`), we cannot delete reliably from cascade — log a TODO and a Phase 11+ ticket instead of silently leaving orphans.
- **Risk: running on shared dev DB.** STATE.md blockers note: "recommend running it on a DB snapshot first." The verification script should ideally rollback or seed-then-cleanup; never run against production.
- **Convention compliance:** Path alias `@/*` → `./src/*` per CLAUDE.md. All imports use `@/db`, `@/db/schema`. No new dependencies added.
