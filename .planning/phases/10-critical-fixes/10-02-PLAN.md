<objective>
Close two CRITICAL audit findings that share the server-entry + security surface:
1. **C3 / CRIT-02:** `/health/ready` currently reports `database.ok=true` even when `checkDatabaseHealth()` returned `{ ok: false }`, blinding monitoring during DB outages. Bug at `src/server/lib/health.ts:11-13`.
2. **C1 / CRIT-03:** `POST /api/mail/mailboxes/test-connection` (handler at `src/server/routes/mail/mailboxes.ts:358`) does NOT verify the authenticated `x-user-id`, does NOT block private/loopback hosts, and has no per-user rate limit — it is currently a SMTP/IMAP proxy for anyone with any valid Supabase JWT.

Purpose: Restore the readiness probe's truth contract (so K8s / monitors react correctly) and close the test-connection proxy (so the server can't be weaponized for internal network probing or credential stuffing).

Output: Three modified files (`health.ts`, `mailboxes.ts`, `index.ts`) producing a truthful readiness endpoint and a hardened test-connection endpoint. Atomic commits per task per CLAUDE.md.
</objective>

## Goal

`/health/ready` tells the truth about DB state, and `/test-connection` rejects unauthenticated callers, private hosts, and high-frequency abuse.

## Scope

**In scope:**
- Fix `src/server/lib/health.ts:11-13` to check `dbResult.value.ok` in addition to `status === 'fulfilled'`. Set HTTP 503 when database is unhealthy.
- Add `if (!userId) return res.status(401).json({...})` at the top of the `/test-connection` handler (around `src/server/routes/mail/mailboxes.ts:358`).
- Add an inline `isPrivateHost(host)` check (copied from `src/server/routes/track.ts` — extraction into `network-guard.ts` is Phase 11 SEC-01) covering smtpHost and imapHost.
- Add a route-scoped `express-rate-limit` instance for `/api/mail/mailboxes/test-connection` (5 req / min keyed by user, falling back to IP if userId missing — but userId guard makes that unreachable).

**Out of scope:**
- Extracting `isPrivateHost` to `src/server/lib/network-guard.ts` (Phase 11 SEC-01).
- IPv6 ULA / link-local coverage and DNS rebinding protection (Phase 11 SEC-01 extension).
- IMAP TLS hardening / `skipTlsVerify` flag (Phase 11 SEC-02).
- JWT cache (Phase 11 SEC-03).
- Refactoring other handlers in `mail/mailboxes.ts`.
- Adding a test framework — verification is curl/manual.

### Task 1: Truth-telling /health/ready

**Type:** auto

**Files:**
- `src/server/lib/health.ts`

**Action:**
1. Read `src/server/lib/health.ts` end-to-end. The bug is at lines ~11–13 per audit C3:
   ```ts
   const database = dbResult.status === 'fulfilled'
     ? { ok: true, latencyMs: dbResult.value.latencyMs }
     : { ok: false, error: ... }
   ```
   This treats `Promise.allSettled` fulfillment as success, but `checkDatabaseHealth()` returns `{ ok, latencyMs, error? }` and CAN fulfill with `ok: false`.
2. Rewrite the database-result branch to:
   ```ts
   const database = dbResult.status === 'fulfilled' && dbResult.value.ok
     ? { ok: true, latencyMs: dbResult.value.latencyMs }
     : {
         ok: false,
         error: dbResult.status === 'fulfilled'
           ? (dbResult.value.error ?? 'database probe returned ok=false')
           : String((dbResult as PromiseRejectedResult).reason),
       };
   ```
3. If there is a similar Supabase auth probe in the same file using the same `status === 'fulfilled'` pattern, apply the same fix only IF its underlying probe also returns `{ ok }`. Inspect first — do not blanket-apply.
4. Locate the HTTP status code decision (somewhere downstream of `database` — possibly in the route handler in `src/server/index.ts` or in `health.ts` itself). Ensure that when `database.ok === false`, the response is HTTP **503** (Service Unavailable), not 200. If the existing code returns 200 unconditionally, add:
   ```ts
   const allOk = database.ok && (otherChecks?.ok ?? true);
   res.status(allOk ? 200 : 503).json({ ok: allOk, database, ... });
   ```
   Adjust to the actual structure observed in the file.
5. Do NOT change the response body shape (consumers may parse `database.ok`); only fix the boolean and the status code.

**B. Open `src/server/index.ts` and add a route-scoped rate limiter.**

1. Find where existing `express-rate-limit` limiters are defined (audit notes: global `/api/` limiter, `authLimiter`, tracking limiter — around lines 38–62 per audit).
2. Add a new limiter near the others:
   ```ts
   const testConnectionLimiter = rateLimit({
     windowMs: 60 * 1000,        // 1 minute
     max: 5,                     // 5 requests / window
     standardHeaders: true,
     legacyHeaders: false,
     keyGenerator: (req) => {
       const uid = req.headers['x-user-id'];
       return typeof uid === 'string' && uid ? `user:${uid}` : `ip:${req.ip}`;
     },
     message: { error: 'Too many connection tests; please wait a minute.' },
   });
   ```
3. Apply it to the exact route BEFORE the router mount. Locate where the mail router is mounted (something like `app.use('/api/mail', mailRouter)`); above it, add:
   ```ts
   app.use('/api/mail/mailboxes/test-connection', testConnectionLimiter);
   ```
   The order matters: this `app.use` must run BEFORE the router mount so the middleware fires on the exact path. If the router mounts at `/api/mail`, the limiter on the full path will still intercept correctly because Express runs middleware in registration order — but verify with a quick test.
4. If `rateLimit` is not yet imported in `index.ts`, import it from `express-rate-limit` (already a dependency per audit context).
