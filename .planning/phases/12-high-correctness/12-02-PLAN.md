<objective>
Close audit finding H4 (click-tracking replay multiplication) by deduplicating click events per `(messageId, token)` within a 60s window. After this plan, hitting a click-tracking URL repeatedly (refresh, email-client preview prefetch, bot crawl) increments `statistics.linksClicked` only once per minute per message.

Purpose: Email clients (especially Outlook, Apple Mail with Privacy Protection, and corporate link-rewriters like Microsoft Safe Links) hit click-tracking URLs multiple times per actual user click — sometimes 5-10 times for a single user action. This inflates `linksClicked` stats by 2-10x, making engagement metrics meaningless. The audit explicitly calls this out (H4). DB-backed dedup is preferred over in-memory because the server may run multi-instance (load-balanced deploys) and an in-memory Map would only dedup within one process.

Approach (per CONTEXT.md "Click replay dedup" decision — DB-backed preferred): add a nullable `clicked_at TIMESTAMP` column to `messages` (mirroring the existing `opened_at` column at schema.ts:247). On each click, read `clicked_at`; if null OR older than 60 seconds, UPDATE it to now AND fire incrementStat + webhook. Otherwise, skip the stat/webhook entirely. The user-facing 302 redirect still happens on every hit — only the analytics side-effect is gated.

Output:
1. Migration 019: `ALTER TABLE messages ADD COLUMN IF NOT EXISTS clicked_at TIMESTAMP` (nullable, no default).
2. `src/db/schema.ts`: add `clickedAt: timestamp('clicked_at')` to the messages block (next to existing `openedAt` field at line 247).
3. `src/server/routes/track.ts` click handler (lines 71-125): after the redirect-issued line (95) and before the async tracking block, gate the `incrementStat` + `fireWebhooks` calls on the dedup check. Use a single UPDATE-with-WHERE-clause to atomically set clicked_at AND determine whether this was the "winning" first-write.

    After:
    ```ts
    // Async tracking with 60s dedup window (COR-03, audit H4)
    try {
        // Atomic dedup gate: write clicked_at = NOW() only if it was NULL or older than 60s.
        // The .returning() tells us whether THIS request was the "winning" first/refresh.
        const updated = await db
            .update(messages)
            .set({ clickedAt: new Date(), updatedAt: new Date() })
            .where(
                and(
                    eq(messages.token, token),
                    or(
                        isNull(messages.clickedAt),
                        lt(messages.clickedAt, sql`NOW() - INTERVAL '60 seconds'`)
                    )
                )
            )
            .returning({ id: messages.id, organizationId: messages.organizationId, subject: messages.subject, fromAddress: messages.fromAddress })

        if (updated.length === 0) {
            // Replay within 60s — token matched a message but dedup window blocked the UPDATE.
            // (Or the token doesn't exist at all — indistinguishable here, but we silently no-op either way.)
            return
        }

        const message = updated[0]
        const trackClicks = true
        const privacyMode = false
        if (!trackClicks || privacyMode) return

        await Promise.allSettled([
            incrementStat(message.organizationId, 'linksClicked'),
            fireWebhooks(message.organizationId, 'link_clicked', {
                messageId: message.id,
                subject: message.subject,
                url: targetUrl,
                clickedAt: new Date().toISOString(),
            }),
        ])
    } catch (err) {
        console.error('Click tracking error:', err)
    }
    ```

- **Migration number collision with 12-01.** Both plans target migration 019 nominally. 12-01's Task 0 only creates 019 if DB drift is detected on `webhook_requests.attempts` (schema confirms it exists, so 019 will be free for 12-02 in the normal case). - **Atomic UPDATE assumption.** The dedup correctness depends on Postgres serializing the WHERE+SET against concurrent UPDATEs on the same row. This is the default behavior (READ COMMITTED isolation + row locks). No explicit transaction or advisory lock is needed for this pattern, which is well-established for "claim a row" patterns. Document this in SUMMARY.md so future readers don't add a redundant lock.
- **Updated.length === 0 conflates "no such token" with "replay hit".** Both legitimately should no-op the analytics path. The original code did a separate `if (!message) return` after a SELECT — we lose that explicit branch but gain atomicity and a single round-trip. Tradeoff is acceptable; the audit didn't ask for differentiated logging here.
- **Clock drift across multi-instance.** The `NOW()` in the SQL expression is server-side (the DB's clock), not the application server's clock, so multi-instance app servers using the same DB share one source of truth. No clock-sync risk.
- **`opened_at` lifetime dedup vs `clicked_at` 60s window inconsistency.** Different semantics — opens are "did this email get opened at all" (binary), clicks are "how often did the user engage" (count). The audit only asks for click dedup; opens already dedup lifetime in track.ts:37. Don't touch the open path. Document the intentional asymmetry in SUMMARY.md.
- **Removing the organization SELECT.** The pre-refactor code SELECTed organizations to gate on existence, but only used it as a boolean. The refactor drops the lookup; the WHERE clause already implicitly filters to messages with valid org via FK. No behavioral change beyond the trackClicks/privacyMode kill-switch (preserved).
