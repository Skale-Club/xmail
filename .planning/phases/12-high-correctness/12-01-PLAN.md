    ```ts
    const BACKOFF_MS = [0, 3000, 9000]   // sleep BEFORE attempt N
    const MAX_ATTEMPTS = 3
    const sleep = (ms: number) => new Promise<void>((r) => setTimeout(r, ms))

    // ... inside fireWebhooks, replacing the matching.map callback body:
    await Promise.allSettled(
        matching.map(async (wh) => {
            const headers: Record<string, string> = {
                'Content-Type': 'application/json',
                'X-Webhook-Event': event,
            }
            if (wh.secret) {
                const sig = createHmac('sha256', wh.secret)
                    .update(JSON.stringify(payload))
                    .digest('hex')
                headers['X-Webhook-Signature'] = `sha256=${sig}`
            }

            // COR-02 — retry transient failures (5xx, timeout, network) up to 3 attempts with exponential backoff
            for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
                if (BACKOFF_MS[attempt - 1] > 0) await sleep(BACKOFF_MS[attempt - 1])

                try {
                    const response = await fetch(wh.url, {
                        method: 'POST',
                        headers,
                        body: JSON.stringify(payload),
                        signal: AbortSignal.timeout(10_000),
                    })
                    const body = await response.text()

                    await db.insert(webhookRequests).values({
                        webhookId: wh.id,
                        event: event as any,
                        payload,
                        responseCode: response.status,
                        responseBody: body.substring(0, 5000),
                        success: response.ok,
                        attempts: attempt,
                    })

                    // Success OR permanent failure (4xx) → stop. Only 5xx triggers retry.
                    if (response.ok || response.status < 500) return
                    // else: 5xx → loop continues (unless this was attempt MAX_ATTEMPTS)
                } catch (err) {
                    // Network/timeout error — record and (if attempts remain) retry.
                    await db.insert(webhookRequests).values({
                        webhookId: wh.id,
                        event: event as any,
                        payload,
                        success: false,
                        error: err instanceof Error ? err.message : 'Request failed',
                        attempts: attempt,
                    })
                    // Loop continues unless this was the last attempt.
                }
            }
        })
    )
    ```

    - One `webhook_requests` row PER ATTEMPT (3 rows for a webhook that fails 3x). `attempts` field set to `attempt` (1, 2, 3).

    - 2xx exits the loop after recording (success).
    - 5xx loops (record then retry, unless attempt == MAX_ATTEMPTS in which case the loop naturally ends).
    - Timeout / network error loops (record then retry, unless attempt == MAX_ATTEMPTS).

<risks>
- **Backoff timing interpretation ambiguity.** Audit says "1s/3s/9s between attempts"; ROADMAP says "timestamps roughly 1s, 4s, 13s apart". Two readings: (a) gaps BETWEEN attempts are 1s/3s/9s → cumulative offsets 0,1s,4s,13s; (b) gaps are 3s/9s with attempt 1 at T=1s of some external delay → cumulative 1s,4s,13s. Plan adopts (a) with BACKOFF_MS=[0,3000,9000] which makes attempts fire at T=0s,3s,12s after fireWebhooks is invoked. ROADMAP language "roughly 1s/4s/13s apart" is satisfied within a 1s tolerance for any T0 in {0..1}s. Document the choice in SUMMARY.md.
- **Retry loop blocks the surrounding Promise.allSettled for up to 13s.** This is bounded and intentional — fireWebhooks is already called from background tracking code (open/click handlers, send pipeline) that does not block the HTTP response. If it were called from a request-response path that needed sub-second latency, the retry should be queued instead. Audit acknowledges this trade-off; v1.3 dead-letter queue would async-ify.
- **AbortSignal.timeout availability.** Node 18+ required (present in dev per package.json engines / Vite stack). If the project somehow targets Node 16, the import `AbortController` polyfill would be needed — verify Node version in package.json/.nvmrc before assuming.
- **Test endpoint exception handler.** When AbortSignal.timeout fires, the thrown error has `name === 'TimeoutError'` and `name === 'AbortError'` depending on Node version. The existing catch block records `err.message` which is sufficient; no need to narrow.
- **Concurrency edge: same webhook firing multiple events simultaneously.** Retry loop is per-(event, attempt), so two events firing concurrently each get their own 3-attempt sequence. webhook_requests rows are timestamped distinctly. No mutex needed.
</risks>
