# Phase 21 Research

## Existing primitives to reuse

- `src/db/schema.ts` already stores full bodies, headers, Message-ID, references, and attachment metadata for general webmail in `mail_messages`, but those rows are user-mailbox scoped rather than outreach-organization scoped.
- `src/server/smtp-server.ts`, `src/server/mx-server.ts`, and `src/server/lib/mail-sync.ts` already parse complete RFC messages with `mailparser` and store native/IMAP messages.
- `src/server/jobs/processReplies.ts` implements three-tier reply matching but external IMAP currently fetches headers only and directly mutates campaign/lead counters. It does not persist a conversation or reply body.
- `src/server/jobs/processBounces.ts` classifies DSNs separately; Phase 19 is expected to resolve the native reply/bounce race and bound provider scans.
- `src/server/lib/outlook.ts` supports sending and token refresh; no Graph incoming/delta client exists yet.
- `src/server/lib/pagination.ts` is page-based. Unified Inbox should use opaque keyset cursors because conversations reorder when new messages arrive.

## Storage design

### `outreach_conversations`

Recommended columns: `id`, `organization_id`, `email_account_id`, nullable `lead_id`, `campaign_id`, `campaign_lead_id`, `provider_thread_id`, `thread_key`, `normalized_subject`, `status`, `last_message_id`, `last_message_at`, `last_inbound_at`, `last_outbound_at`, `latest_message_preview`, `created_at`, `updated_at`.

Use a unique tenant thread key such as `(organization_id, email_account_id, thread_key)`. `thread_key` is generated by the normalizer from a provider thread id or the root RFC Message-ID; address-only heuristic conversations use a generated UUID and are later mergeable without weakening uniqueness.

### `outreach_conversation_messages`

Recommended columns: `id`, `organization_id`, `conversation_id`, `email_account_id`, nullable `outreach_email_id`, `direction`, `provider`, `provider_message_id`, `provider_thread_id`, `source_key`, `internet_message_id`, `in_reply_to`, `references`, `subject`, `from_address`, address JSON arrays, `plain_body`, `html_body`, safe `headers`, attachment metadata JSON, `has_attachments`, `classification`, `match_strategy`, `sent_at`, `received_at`, `created_at`.

Use unique `(organization_id, email_account_id, source_key)`. Keep RFC ids indexed, normalized, and scoped, but not unique.

### Participants, provider staging/cursors, read state

- Participants: one row per normalized address/role per conversation; unique within organization/conversation/address/role.
- Phase 19 staging/cursors: `outreach_provider_events` is unique by `(organization_id, email_account_id, provider, provider_message_id)` and carries normalized headers/bodies/classification plus attachment metadata; `outreach_provider_cursors` carries leases, errors/retry, Graph delta, and IMAP UID metadata. Phase 21 consumes these rows and adds columns only if the landed contract lacks a required state; it does not create a second cursor/poller system.
- Phase 21 adds a separate provider-event materialization lifecycle: pending/processing/materialized/failed, lease expiry, bounded attempts, sanitized error, `materialized_at`, and normalized-message id. This is deliberately distinct from Phase 19 `processed_at`; reply/bounce classification may finish before or after inbox materialization.
- Read state: unique organization/conversation/user; record `last_read_message_id`, `read_at`, `updated_at`. The list API computes unread from `last_inbound_at > read_at` (or no state).

## Ingestion architecture

Create a provider-neutral `ingestOutreachMessage(input)` service. The input contains organization/account/source identity, normalized headers/bodies/addresses, and provider timestamps. The service:

1. verifies account belongs to organization;
2. checks `source_key` idempotency;
3. classifies DSN/auto-reply/human message;
4. resolves outreach attribution inside the same organization/account;
5. finds or creates a conversation;
6. inserts immutable message + participants;
7. updates conversation summary;
8. emits a post-commit domain result used exactly once by reply metrics/notification/follow-up scheduling.

Do not let provider loops reproduce matching or side-effect logic. Refactor `processReplies.ts` to call this service, then base `markAsReplied` on the returned first-ingestion result.

Outbound campaign/manual/agentic history enters through the same conversation model from persisted `outreach_emails`. Use deterministic `outreach-email:<uuid>` source keys and materialize only rows whose successful send state and `sent_at` are durable. The exclusive live hook is inside `src/server/lib/outreach-dispatch.ts`, immediately after that durable update; campaign/manual/agentic entrypoints call only the dispatcher and never invoke inbox materialization. A bounded anti-join backfill (`NOT EXISTS` normalized source key, ordered by `sent_at,id`) is inherently restartable and fills failures without a second checkpoint table. Materialize outbound roots before/retry alongside inbound events so `In-Reply-To` and `References` attach to the same conversation.

## Provider cursors

- Native: scan `mail_messages.id/created_at` after a durable high-water mark, filter account companion mailbox and folder, and use `native:<mail_message_uuid>` as source key.
- IMAP: persist UIDVALIDITY + last UID per folder; source key `imap:<uidvalidity>:<uid>`. On UIDVALIDITY change, reset cursor and rely on source-key/RFC dedupe during a bounded resync.
- Graph: use `/messages/delta` per mailbox/folder, persist `@odata.deltaLink`; source key uses Graph immutable id. Handle 410/invalid cursor by clearing only that mailbox cursor and bounded resyncing recent messages.

Outlook OAuth scopes will need read access (`Mail.Read` or least-privilege equivalent) in addition to send access. The executor must update consent/version handling and force reconnect if existing tokens lack required scope; never silently mark those accounts healthy.

## Search and pagination

- Cursor encodes `(last_message_at, id)` and filter fingerprint, signed or validated server-side. Query order is `last_message_at DESC, id DESC`.
- Limit max 100; detail message order is `COALESCE(received_at, sent_at, created_at) ASC, id ASC`.
- MVP keyword search uses escaped `ILIKE` over subject, participant address/name, and latest preview; full body search can be included only with an indexed `tsvector`. Never load all rows and filter in JavaScript.
- Return `nextCursor`, `hasMore`, and filter-derived counts; do not return credentials, raw auth headers, or provider tokens.

## Testing strategy

- Unit: Message-ID/address normalization, reference tokenization, classification, cursor encoding, source-key construction.
- Database integration: duplicate delivery, concurrent duplicate insert, thread resolution, tenant isolation, cursor recovery, rollback before cursor advance.
- Route integration: org A cannot infer/list/detail/read-state org B; viewer read access works; malformed cursors and oversize limits fail closed.
- Provider fixtures: native parsed message, raw IMAP MIME with html/text/attachment metadata, Graph delta payload, duplicate/reordered replay, expired delta cursor.

## Migration and rollout risks

- No bulk backfill of all historical `mail_messages` in the migration. Ship empty tables, then a bounded/restartable backfill job for recent outreach-related messages.
- `mail_messages.message_id` may be null or duplicated; do not add uniqueness there.
- Large HTML bodies require response projection: list endpoints return preview only; detail hydrates bodies.
- Cursor advancement must be after transaction commit. One malformed message should be quarantined/recorded so the account can continue without silently losing it.
- Attachment metadata may contain unsafe filenames; sanitize on output and defer binary storage/download to Phase 22.
