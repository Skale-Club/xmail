<objective>
Close two distinct correctness audit findings in a single plan:

**H10 (COR-05)** — Folder ownership bypass: `POST /api/mail/mailboxes/:mailboxId/messages/:messageId/move` (`src/server/routes/mail/messages.ts:627`) accepts a `folderId` and writes it to `mailMessages.folderId` without verifying the folder belongs to the same `mailboxId`. A user can move their own message into a folder owned by ANOTHER user's mailbox, silently corrupting the folder tree (the message becomes invisible to its owner and appears as orphaned in the foreign mailbox).

**H11 (COR-06)** — Suppression list bypass: `POST /api/messages` (`src/server/routes/messages.ts:195`) does NOT consult the `suppressions` table before queueing a send. Users on the suppression list (bounce/complaint/manual unsubscribe) receive emails anyway, exposing the org to spam complaints and abuse reports.

Both bugs share a corrective shape — validate-before-write — so we pack them in one plan. Files are disjoint: H10 lives in `src/server/routes/mail/messages.ts` (user mail module), H11 lives in `src/server/routes/messages.ts` (server send module). No file conflict; can land as a single commit.

Purpose:
1. COR-05 prevents cross-mailbox folder corruption — a user with mailbox A cannot move a message in A into a folder owned by mailbox B even via direct API call.
2. COR-06 makes the suppression list actually do its job. Currently it's populated by the bounce/complaint pipeline but never consulted at send time. Closing this is critical for deliverability and compliance.

Output:
1. `src/server/routes/mail/messages.ts /move` handler: BEFORE the `db.update(mailMessages)`, SELECT from `mailFolders WHERE id = folderId AND mailboxId = req.params.mailboxId`. If null → 400 "Folder does not belong to this mailbox".
2. `src/server/routes/messages.ts POST /` handler: AFTER Zod parse and access check, BEFORE the `db.insert(messages)`, query `suppressions WHERE organizationId = data.organizationId AND emailAddress = ANY (to+cc+bcc)` using `inArray`. If any rows returned → 400 with `{ error: 'Recipients are suppressed', suppressed: [<emails>] }`.
</objective>

<risks>
- **Duplicate `const allRecipients` declaration after Task 2 Edit 2.** The existing handler declares `allRecipients` at line ~290 for the deliveries insert. Task 2 declares it earlier (around line 210). Executor MUST remove the line 290 declaration; otherwise tsc fails with "Cannot redeclare block-scoped variable". Verification grep catches this (must equal 1).
- **`inArray` empty-array behavior in Drizzle.** If `allRecipients` is empty (no `to`, `cc`, `bcc`), `inArray(...)` on an empty array generates `WHERE FALSE` in some Drizzle versions — safe (returns 0 rows). The current Zod schema requires `to.array().min(1)`, so the empty case shouldn't happen via this endpoint, but the `allRecipients.length > 0` guard makes it explicit.
- **Case sensitivity of emailAddress.** The suppression table stores emails as inserted; the recipient list comes from user input. If suppressions inserts lowercase but recipients arrive mixed-case, the match misses. This is a known broader issue (QUA-04 Phase 13 will lowercase domains; emails are a similar story). Document as a SUMMARY.md follow-up: "Future hardening: normalize recipient emails to lowercase before suppression check, and normalize on insert into suppressions."
- **Batch move endpoint not covered.** The `/batch` action at line 662 also accepts `folderId` for custom-folder moves and doesn't validate ownership. Audit only flags `/move`; we mirror the audit scope. TODO logged in SUMMARY.md.
- **Outreach send path bypasses suppression.** `src/server/lib/outreach-*` does its own sending and doesn't consult `suppressions`. Audit only flags `POST /api/messages` (the platform send). Document in SUMMARY.md as a v1.3 follow-up.
- **Performance of inArray on huge recipient lists.** For ≤100 recipients (sendMessageSchema doesn't enforce a max on `to.array()` but Zod max body is 5MB so practically ≤a few thousand), inArray performs fine with the unique index `(organizationId, emailAddress)`. No concern at typical scale.
</risks>
